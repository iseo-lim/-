# 요청 창구

운영팀이 기획·개발·디자인에 보내던 슬랙 DM·구두 요청을 한곳에서 받고, 그 요청이 앱·바리스온·키오스크의 어느 버전에 담겨 언제 배포되는지까지 관리하는 사내 페이지예요.

## 기능

| 메뉴 | 하는 일 |
|---|---|
| 요청 등록 | 긴급도·중요도와 **그 이유**를 반드시 적게 해요 |
| 요청 보드 · 요청 목록 | 요청이 어느 단계인지 봐요. 권한에 따라 자기 팀 요청만 보거나 전체를 봐요 |
| 우선순위 회의 | 기획·개발·디자인·운영이 함께 우선순위(즉시 대응·높음·보통·낮음)를 확정해요 |
| 버전 관리 | 앱·바리스온·키오스크 버전마다 담긴 요청, 배포 예정일, 배포 기록, 릴리스 노트를 관리해요 |
| 권한 관리 | 사람별 역할과 역할별로 할 수 있는 일을 정해요 (관리자) |
| 알림 기록 | 보낸(또는 보낼) 슬랙 알림을 봐요 (관리자) |

## 회사 규칙과 맞춘 것 (task-management 「티켓 관리 규칙 v2」)

상태·유형·우선순위·버전 이름은 `xyzcorpsoftware/task-management`의 보드 칸과 라벨을 그대로 따라요. 앱(`lounge-x-app`)과 API(`api-loungexr-app`) 저장소는 PR이 머지되면 이 보드의 칸을 옮기는 구조라, 요청 창구도 같은 말을 써요.

| 구분 | 요청 창구 (화면) | 회사 보드·라벨 |
|---|---|---|
| 상태 | 접수 | (요청 창구에만 있음: 우선순위 회의 전) |
| | 백로그 → 기획·디자인 → 개발 대기 → 개발 → QA → 배포 대기 → 완료 | 보드 칸 `Backlog → 기획·디자인 → 개발 대기 → 개발 → QA → 배포 대기 → 완료` |
| | 보류 / 반려 | 반려는 이슈를 `not planned`로 닫음 |
| 유형 | 버그 / 신규 기능 / 기능 개선 / 운영 지원 / 논의 필요 | `type: bug / feature / improvement / chore / discussion` |
| 우선순위 | 즉시 대응 / 높음 / 보통 / 낮음 | `priority: critical / high / medium / low` (내부 값 P0~P3, 화면에는 안 보여요) |
| 플랫폼 | 앱 / 바리스온 / 키오스크 | `project: Lounge(x) APP / BarisON / X KIOSK` |
| 버전 | 앱 v2.3.0, 바리스온 2026-11 | 마일스톤 `Lounge(x) v2.3.0`, `BarisON 2026-11` (바리스온은 월 단위) |

### 요청이 배포까지 가는 흐름

1. 운영 쪽이 요청을 등록해요. 상태는 `접수`예요.
2. 우선순위 회의에서 우선순위와 담당자를 정해요. 상태는 `백로그`가 돼요.
3. 담당자가 진행에 따라 상태를 `기획·디자인 → 개발 대기 → 개발`로 옮기고, 요청 상세에서 **반영 버전**을 골라요. 버전 상세에서 요청을 **담아도** 돼요. 요청 대상 플랫폼마다 버전을 하나씩 고를 수 있어요.
4. 버전 상태를 `계획 → 개발 중 → QA → 배포 대기`로 바꿔요. 버전이 `QA`·`배포 대기`가 되면 담긴 요청(개발 중인 것)도 같은 칸으로 따라가요.
5. 배포가 끝나면 **배포 완료로 표시**를 눌러요.
   - 그 버전에 담긴 요청이 `완료`로 바뀌어요. 바리스온·앱처럼 여러 플랫폼에 걸친 요청은 모든 플랫폼 버전이 배포돼야 완료돼요.
   - 요청자에게 "요청하신 내용이 앱 v2.3.0에 반영돼 배포됐어요" 슬랙 알림이 가요.
   - 채널에는 배포된 버전과 담긴 요청 목록이 올라가요.

**요청 번호(REQ-N)**: 요청을 등록한 순서대로 1부터 하나씩 늘어나는 고유 번호예요. 지우거나 반려해도 번호를 다시 쓰지 않아서 번호만으로 요청을 찾을 수 있어요. Jira의 `PROJ-123`이나 회사 보드의 `TM#123`과 같은 방식이에요.

**릴리스 노트**: 버전 상세의 '담긴 요청으로 초안 만들기'를 누르면 담긴 요청 제목으로 초안이 만들어져요(새로워진 점 / 고친 점).

## 실행

Node.js 20 이상만 있으면 돼요. 설치할 외부 패키지는 없어요.

```powershell
cd "C:\Users\iseol\Desktop\사내요청 통합"
node server.js            # 실행
node server.js --seed     # 테스트 모드에서, 데이터가 비어 있으면 예시 요청 7건과 버전 7개를 넣고 실행
```

`http://localhost:8080`으로 접속해요. 서버를 켠 PowerShell 창을 닫으면 서버도 꺼져요. 코드를 바꾼 뒤에는 **Ctrl+C**로 끄고 다시 실행해야 반영돼요.

`config.json`이 없으면 `config.example.json`으로 실행돼요. 이때는 테스트 로그인 모드이고, 테스트 계정의 비밀번호는 모두 `1234`예요.

## 권한

역할은 다섯 가지예요. 역할마다 할 수 있는 일은 **권한 관리 → 역할별 권한**에서 바꿀 수 있어요.

| 할 수 있는 일 | 관리자 | 리드 | 작업자 | 운영 리드 | 요청자 |
|---|:-:|:-:|:-:|:-:|:-:|
| 모든 팀의 요청 보기 | ✓ | ✓ | ✓ | ✓ | |
| 우선순위 회의 (우선순위·담당자 지정, 보류·반려) | ✓ | ✓ | | ✓ | |
| 요청 처리 담당 (담당자 후보, 맡은 요청 상태 변경) | ✓ | ✓ | ✓ | | |
| 버전 등록·수정, 요청 담기, 배포 완료 처리 | ✓ | ✓ | ✓ | | |
| 권한 관리, 알림 기록 | ✓ | | | | |

- 모든 사람은 요청 등록, 자기 팀 요청 보기, 댓글 쓰기, 버전 목록 보기를 할 수 있어요.
- 기본 역할은 통합계정 권한그룹(`groupMap`)으로 정해져요. 관리자가 **권한 관리 → 사람별 역할**에서 사람마다 바꿀 수 있어요.
- 관리자는 자기 역할을 바꿀 수 없어요. 관리자가 모두 잠기는 일을 막으려면 `admins`에 아이디를 한 명 이상 넣어 두세요.

## 설정 (`config.json`)

`config.example.json`을 `config.json`으로 복사해서 고쳐요. 토큰 같은 민감한 값은 환경변수로 넣는 걸 권장해요.

| 항목 | 설명 | 환경변수 |
|---|---|---|
| `port` / `host` | 서버 포트·주소 | `PORT`, `HOST` |
| `baseUrl` | 이 페이지의 접속 주소. 슬랙·GitHub 링크에 쓰여요 | `BASE_URL` |
| `sso.mode` | `real`은 통합계정, `mock`은 테스트 계정. **사내 배포 때는 반드시 `real`** | `SSO_MODE` |
| `sso.baseUrl` | 통합계정 서버 주소 | `SSO_BASE_URL` |
| `admins` | 항상 관리자인 사람의 아이디 목록 | |
| `groupMap` | 통합계정 권한그룹 → 팀·직군·역할 | |
| `boardShowsAllTeams` | `true`면 요청자도 다른 팀 요청의 제목·상태를 봐요 (보드·버전 화면) | |
| `github.token` / `github.defaultRepo` / `github.repoByPlatform` | 요청 접수 시 GitHub 이슈 만들기 | `GITHUB_TOKEN` |
| `slack.webhookUrl` | 채널 알림용 Incoming Webhook | `SLACK_WEBHOOK_URL` |
| `slack.botToken` | 요청자·담당자 DM용 봇 토큰 | `SLACK_BOT_TOKEN` |
| `sessionHours` | 로그인 유지 시간 (기본 12) | |
| `dataDir` | 데이터 폴더 (기본 `data/`) | `DATA_DIR` |

### 권한그룹 매핑 (`groupMap`)

```json
"groupMap": {
  "실제_기획리드_그룹ID": { "team": "기획팀", "job": "기획", "role": "lead" },
  "실제_개발_그룹ID":     { "team": "개발팀", "job": "개발", "role": "member" },
  "실제_운영_그룹ID":     { "team": "운영팀", "job": "운영", "role": "requester" }
}
```

- `role`에는 `admin`, `lead`, `member`, `opsLead`, `requester` 중 하나를 넣어요.
- `groupMap`에 없는 그룹만 가진 사람은 로그인할 수 없어요(403).
- **예시의 `REQ_*` ID는 임시 값이에요.** 실제 권한그룹 ID는 통합계정 담당자에게 받아서 바꿔야 해요.

## 통합계정 SSO 연동

연동 가이드의 2단계 로그인 흐름을 그대로 구현했어요.

1. 브라우저가 통합계정에 ID/PW를 보내요(`public/app.js`). 비밀번호는 이 서버로 오지 않아요.
2. 받은 15초짜리 임시 Token을 이 서버 `POST /api/login`으로 바로 넘겨요.
3. 서버가 통합계정 `/api/auth/login/complete`로 확인하고, 권한그룹을 검사한 뒤 HttpOnly 쿠키 세션을 발급해요(`server.js`).

Second Token 자동 로그인(`sso-login`)은 가이드에 API 상세가 없어 빠져 있어요.

## GitHub 연동 (요청 → 이슈)

**지금은 꺼져 있어요.** `config.json`에 GitHub 토큰(`github.token` 또는 환경변수 `GITHUB_TOKEN`)과 이슈를 만들 저장소(`github.defaultRepo`)가 둘 다 있어야 켜져요. 둘 중 하나라도 없으면 화면에 '연동 전'으로 나와요.

- 요청이 접수되면 `[REQ-번호]` 이슈를 만들어요. 라벨은 회사 라벨 체계를 그대로 써요: `project: …`(플랫폼), `type: …`(유형).
- 우선순위가 정해지면 `priority: critical/high/medium/low` 라벨을 달고, 상태·반영 버전이 바뀌면 이슈에 댓글을 남겨요.
- 완료되면 이슈를 닫고, 반려되면 '계획 안 함(not planned)'으로 닫아요.
- 토큰은 대상 저장소에 **Issues: Read and write** 권한만 있으면 돼요.
- 플랫폼별 `project:` 라벨이 다르면 `github.projectLabels`로 바꿀 수 있어요. 예: `{"앱": "project: Lounge(x) APP"}`

**`task-management`에 바로 연결할 때 주의할 점**: 그 저장소에는 규칙 v2를 집행하는 봇이 돌고 있어요. 부모 Epic이 없는 이슈는 Backlog 재결정 주기(30영업일)와 주간 리포트 대상이 되고, `project:`·`type:` 라벨이 없으면 위반으로 잡혀요. 요청 창구가 만드는 이슈는 두 라벨을 항상 달지만, 처음에는 개인 저장소로 시험해 보는 걸 권장해요.

## 슬랙 연동

- **채널 알림**: 새 요청, 상태·우선순위 변경, 버전 상태 변경과 배포 완료가 올라가요.
- **DM**: 요청자·담당자에게 보내요. 요청이 담긴 버전이 배포되면 요청자에게도 보내요. 필요한 스코프는 `chat:write`, `users:read`, `users:read.email`이에요.
- 설정 전에는 실제로 보내지 않고 **알림 기록**에만 남아요.

## 디자인

- **테마**: theme-factory의 **Arctic Frost**를 웹 화면에 맞게 넓혀 썼어요.
- **글꼴**: 본문은 Pretendard, 요청 번호·버전 번호·날짜는 JetBrains Mono예요. 두 글꼴 모두 `public/fonts`에 들어 있어요(SIL OFL).
- **버전 화면**: 플랫폼별 세로 배포 레인이에요. 빈 원은 예정된 버전, 채워진 원은 배포된 버전이에요.

## MVP에서 뺀 것

- 스프린트·백로그·에픽·작업 단위 관리(Jira형 기능)와 GitHub 작업·PR 동기화는 뺐어요. 코드는 git 기록에 남아 있어서 필요하면 되살릴 수 있어요.
- 저장소가 JSON 파일이라 동시 사용자가 수십 명 수준일 때까지만 적합해요.
- 키오스크 매장·기기별로 어떤 버전이 깔려 있는지 추적하는 기능은 없어요.
