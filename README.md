# 요청 창구

운영팀이 기획·개발·디자인에 보내던 슬랙 DM·구두 요청을 한곳에서 받고, 그 요청을 작업으로 나눠 스프린트로 관리하는 사내 페이지예요. 작업은 GitHub 이슈·PR과 양방향으로 맞춰져요.

## 기능 한눈에 보기

| 메뉴 | 하는 일 |
|---|---|
| 요청 등록 | 긴급도·중요도와 **그 이유**를 반드시 적게 해요 |
| 요청 보드 · 요청 목록 | 요청이 어느 단계인지 봐요. 권한에 따라 자기 팀 요청만 보거나 전체를 봐요 |
| 우선순위 회의 | 기획·개발·디자인·운영이 함께 P0~P3를 확정해요 |
| 스프린트 보드 | 진행 중인 스프린트의 작업을 칸반으로 보고, 카드를 끌어서 상태를 바꿔요 |
| 백로그 | 작업을 끌어서 스프린트에 넣고 순서를 정해요. 스프린트를 만들고 시작해요 |
| 에픽 | 여러 작업을 큰 묶음으로 모아 진행률을 봐요 |
| 권한 관리 | 사람별 역할, 역할별로 할 수 있는 일, 연동 상태를 관리해요 (관리자) |
| 알림 기록 | 보낸(또는 보낼) 슬랙 알림을 봐요 (관리자) |
| 버전 관리 | 준비 중이에요. 지금은 요청의 '반영 버전'으로 모아 보여줘요 |

**요청과 작업이 이어지는 방식**
- 요청 상세에서 **작업으로 쪼개기**를 누르면, 요청의 우선순위와 저장소를 물려받은 작업이 생겨요.
- 작업 중 하나라도 시작되면 요청이 '진행 중'이 되고, 모든 작업이 끝나면 요청이 '완료'로 바뀌어요. 이때 요청자에게 슬랙 알림이 가요.
- 운영 쪽(요청자)은 작업 관리 메뉴는 못 보지만, 자기 요청의 작업 목록과 진행률은 요청 상세에서 볼 수 있어요.

## 실행

Node.js 20 이상만 있으면 돼요. 설치할 외부 패키지는 없어요.

```powershell
cd "C:\경로\사내요청 통합"
node server.js            # 실행
node server.js --seed     # 테스트(mock) 모드에서, 데이터가 비어 있으면 예시 데이터를 넣고 실행
```

`http://localhost:8080`으로 접속해요. `config.json`이 없으면 `config.example.json`으로 실행돼요. 이때는 테스트 로그인 모드이고, 테스트 계정의 비밀번호는 모두 `1234`예요.

## 권한

역할은 다섯 가지예요. 역할마다 할 수 있는 일은 **권한 관리 → 역할별 권한**에서 바꿀 수 있어요.

| 할 수 있는 일 | 관리자 | 리드 | 작업자 | 운영 리드 | 요청자 |
|---|:-:|:-:|:-:|:-:|:-:|
| 모든 팀의 요청 보기 | ✓ | ✓ | ✓ | ✓ | |
| 우선순위 회의 (우선순위·담당자 지정, 보류·반려) | ✓ | ✓ | | ✓ | |
| 작업 관리 보기 | ✓ | ✓ | ✓ | | |
| 작업 만들기·수정·상태 변경 (담당자 후보) | ✓ | ✓ | ✓ | | |
| 스프린트·에픽 관리, 작업 삭제 | ✓ | ✓ | | | |
| 권한 관리·알림 기록·연동 관리 | ✓ | | | | |

- 모든 사람은 요청 등록, 자기 팀 요청 보기, 댓글 쓰기를 할 수 있어요.
- 기본 역할은 통합계정 권한그룹(`groupMap`)으로 정해져요. 관리자가 **권한 관리 → 사람별 역할**에서 사람마다 바꿀 수 있고, '통합계정 기본값'으로 되돌릴 수 있어요.
- 관리자는 자기 역할을 바꿀 수 없어요. 관리자가 모두 잠기는 일을 막으려면 `admins`에 최소 한 명의 아이디를 넣어 두세요. 여기 지정된 사람은 항상 관리자예요.

## 설정 (`config.json`)

`config.example.json`을 `config.json`으로 복사해서 고쳐요. 토큰 같은 민감한 값은 환경변수로 넣는 걸 권장해요.

| 항목 | 설명 | 환경변수 |
|---|---|---|
| `port` / `host` | 서버 포트·주소 | `PORT`, `HOST` |
| `baseUrl` | 이 페이지의 접속 주소. 슬랙·GitHub 링크에 쓰여요. `https://`면 쿠키에 `Secure`가 붙어요 | `BASE_URL` |
| `sso.mode` | `real`은 통합계정, `mock`은 테스트 계정. **사내 배포 때는 반드시 `real`** | `SSO_MODE` |
| `sso.baseUrl` | 통합계정 서버 주소. 환경별 주소는 통합계정 담당자에게 확인 | `SSO_BASE_URL` |
| `admins` | 항상 관리자인 사람의 아이디 목록 | |
| `groupMap` | 통합계정 권한그룹 → 팀·직군·역할 (아래 참고) | |
| `boardShowsAllTeams` | `true`면 요청자도 요청 보드에서 다른 팀 요청의 제목·상태를 봐요 | |
| `github.token` | GitHub 토큰 | `GITHUB_TOKEN` |
| `github.apiUrl` | 기본값 `https://api.github.com`. GitHub Enterprise면 `https://호스트/api/v3` | `GITHUB_API_URL` |
| `github.defaultRepo` | 기본 저장소 (`org/repo`) | |
| `github.repoByPlatform` | 플랫폼별 저장소. 예: `{"앱":"org/app","웹":"org/web","키오스크":"org/kiosk"}` | |
| `github.repos` | 작업 만들 때 고를 수 있는 저장소 추가 목록 | |
| `github.pollSeconds` | GitHub에서 변경을 받아오는 주기(초). 기본 60, 최소 15 | `GITHUB_POLL_SECONDS` |
| `slack.webhookUrl` | 채널 알림용 Incoming Webhook | `SLACK_WEBHOOK_URL` |
| `slack.botToken` | 요청자·담당자 DM용 봇 토큰 | `SLACK_BOT_TOKEN` |
| `sessionHours` | 로그인 유지 시간 (기본 12) | |
| `dataDir` | 데이터 폴더 (기본 `data/`) | `DATA_DIR` |

### 권한그룹 매핑 (`groupMap`)

```json
"groupMap": {
  "실제_기획리드_그룹ID": { "team": "기획팀", "job": "기획", "role": "lead" },
  "실제_개발_그룹ID":     { "team": "개발팀", "job": "개발", "role": "member" },
  "실제_운영_그룹ID":     { "team": "운영팀", "job": "운영", "role": "requester" }
}
```

- `role`에는 `admin`, `lead`, `member`, `opsLead`, `requester` 중 하나를 넣어요.
- 한 사람이 여러 그룹에 속하면 각 역할의 권한을 합쳐서 가져요.
- `groupMap`에 없는 그룹만 가진 사람은 로그인할 수 없어요(403). 연동 매뉴얼 5.3의 "권한그룹 반드시 확인"에 해당해요.
- **예시의 `REQ_*` ID는 임시 값이에요.** 실제 권한그룹 ID는 통합계정 담당자에게 받아서 바꿔야 해요.

## 통합계정 SSO 연동

연동 가이드(`Manual for Integration work.md`)의 흐름을 그대로 구현했어요.

| 단계 | 구현 위치 |
|---|---|
| ① ID/PW → 통합계정 `/api/auth/login` | 브라우저 (`public/app.js`의 `doLogin`). 비밀번호는 이 서버로 오지 않아요 |
| ② `tempToken`, `secondToken` 받기 | `secondToken`은 sessionStorage에 보관 (다른 시스템 SSO용) |
| ③ `tempToken` → 이 서버 `POST /api/login` | 받자마자 바로 전달 (15초 제한) |
| ④⑤ 서버 → 통합계정 `/api/auth/login/complete` | `server.js`의 `ssoComplete` (서버 대 서버) |
| ⑥ 권한그룹 확인 후 자체 세션 발급 | `groupMap` 확인 → 세션 생성 |
| ⑦ 세션 응답 | HttpOnly 쿠키 (`rq_sid`) |

- **구현하지 않은 것**: 매뉴얼 6장의 Second Token 자동 로그인(`sso-login`)은 가이드에 API 상세가 없어 빠져 있어요. Swagger에서 스펙을 확인하면 추가할 수 있어요.
- **CSP**: 브라우저가 통합계정 서버를 직접 호출하므로, `sso.baseUrl`의 출처가 Content-Security-Policy의 `connect-src`에 자동으로 들어가요.

## GitHub 연동 (양방향)

**설정**
1. GitHub 토큰을 만들어요. Fine-grained 토큰이면 대상 저장소에 **Issues: Read and write**와 **Pull requests: Read** 권한을 줘요. 조직 저장소라면 봇 계정으로 만드는 걸 권장해요.
2. `GITHUB_TOKEN`과 저장소(`defaultRepo`, `repoByPlatform`)를 설정하고 서버를 다시 켜요.

**요청 창구 → GitHub** (바뀌는 즉시)

| 요청 창구에서 | GitHub에서 |
|---|---|
| 요청 접수 | `[REQ-번호]` 이슈 생성 (라벨: `요청창구`, `플랫폼:…`, `유형:…`) |
| 요청 우선순위·상태 변경 | 댓글, `우선순위:P1` 라벨, 완료·반려 시 이슈 닫힘 |
| 작업 생성 | `[TASK-번호]` 이슈 생성. 요청 이슈의 **하위 이슈(sub-issue)**로 연결 |
| 작업 상태 변경 | `상태:진행 중` / `상태:리뷰` 라벨, 완료 시 이슈 닫힘 |
| 작업 제목·댓글 | 이슈 제목·댓글 |
| 작업 삭제 | 이슈를 '계획 안 함(not planned)'으로 닫음 |

**GitHub → 요청 창구** (`pollSeconds`마다 주기적으로 조회)

| GitHub에서 | 요청 창구에서 |
|---|---|
| 작업 이슈 닫기·다시 열기, 상태 라벨 변경 | 작업 상태 변경 |
| 작업 이슈 제목 변경 | 작업 제목 변경 |
| 이슈 댓글 | 작업·요청 기록에 댓글 추가 (요청 댓글은 요청자에게 슬랙 DM) |
| PR 제목·본문에 `TASK-번호` 또는 `Closes #이슈번호` | 작업에 PR 연결 |
| PR 열림 (draft 제외) | 작업 '리뷰' |
| PR 머지 | 작업 '완료' → 요청의 작업이 모두 끝나면 요청도 '완료' |

- 사내 서버가 GitHub을 조회하는 방식이라 **사내 서버를 외부에 열 필요가 없어요.**
- 요청 창구와 GitHub이 동시에 바뀌어도, 마지막으로 맞춘 상태와 비교해서 실제로 바뀐 쪽만 반영해요.
- **GitHub Projects 보드도 쓰려면** Project 설정 → Workflows → **Auto-add to project**를 켜고 필터를 `label:작업`으로 두세요. 단, Projects의 Status 칸은 아직 동기화하지 않아요. 상태는 라벨과 이슈 열림/닫힘으로 맞춰요.
- 담당자는 GitHub 아이디와 연결하지 않아서 GitHub 이슈의 Assignee로는 들어가지 않아요.

## 슬랙 연동

- **채널 알림**: Incoming Webhook URL을 `SLACK_WEBHOOK_URL`에 넣어요. 신규 접수, 상태·우선순위 변경이 올라가요.
- **DM**: 봇 토큰을 `SLACK_BOT_TOKEN`에 넣어요. 필요한 스코프는 `chat:write`, `users:read`, `users:read.email`이에요. 통합계정 이메일로 슬랙 사용자를 찾아서 요청자·담당자에게 보내요.
- 설정 전에는 실제로 보내지 않고 **알림 기록**에만 남아요.

## 사내 배포 체크리스트

- [ ] `sso.mode`를 `real`로 바꾸고 `sso.baseUrl`을 운영 주소로 설정
- [ ] `groupMap`에 실제 권한그룹 ID와 역할 입력, `admins`에 관리자 아이디 입력
- [ ] HTTPS 리버스 프록시(nginx 등) 뒤에서 실행하고 `baseUrl`을 `https://…`로 설정
- [ ] 서비스로 등록 (pm2, systemd, Windows 서비스 등)
- [ ] `data/` 폴더 백업 (`data/db.json`, 첨부 `data/uploads/`)
- [ ] GitHub·슬랙 토큰은 환경변수로 설정. `config.json`은 저장소에 올리지 않기

## 디자인

- **테마**: theme-factory의 **Arctic Frost**를 웹 화면에 맞게 넓혀 썼어요. 원색 4가지는 아이스 블루 `#d4e4f7`, 스틸 블루 `#4a6fa5`, 실버 `#c0c0c0`, 화이트 `#fafafa`예요.
- **글꼴**: 본문은 Pretendard, 작업 번호·포인트·날짜는 JetBrains Mono예요. 두 글꼴은 `public/fonts`에 들어 있어서 사내망에서도 외부 CDN 없이 보여요(SIL OFL 라이선스).
- **진행 막대**: 상태별 스토리 포인트를 보여주는 막대가 사이드바·스프린트 보드·백로그·에픽·요청 상세에 공통으로 쓰여요.

## 프로토타입 한계

- 저장소가 JSON 파일이라 동시 사용자가 수십 명 수준일 때까지만 적합해요. 본 서비스로 갈 때는 DB(PostgreSQL 등)로 옮겨야 해요.
- 담당자 후보는 한 번 이상 로그인한 '작업' 권한 사용자예요. 통합계정에 사용자 목록 API가 있다면 그걸로 바꾸는 게 좋아요.
- 요청자가 등록한 뒤 본문을 고치는 기능은 없어요. 추가 내용은 댓글로 남겨요.
- 번다운 차트, 작업 간 의존 관계, 하위 작업(서브태스크)은 아직 없어요.
